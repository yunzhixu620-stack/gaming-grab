## D-05: 架构原则 = 功能域隔离与模块解耦

| 字段 | 值 |
|------|-----|
| **决策ID** | D-05 |
| **日期** | 2026-05-06 10:11 |
| **决策者** | 用户 (minions) |
| **状态** | ✅ CONFIRMED |
| **结论** | 分部分开发，改一个地方不影响全局。功能域隔离。 |

### 原话引用
> "但我希望有一点就是分部分开发，这样互相不会造成影响，
> 我不想要我想要改一个地方全局的链接都乱了"

### 具体措施
1. `features/` 下每个 Phase 独立文件夹
2. 后端每个 router 独立文件，不 cross-import
3. 共享包单向依赖
4. Phase 间通过 project_id + JSON 文件传递数据

### 影响范围
- 目录结构设计
- 开发规范
- Code Review 标准

## D-06: 版本管理与回退机制

| 字段 | 值 |
|------|-----|
| **决策ID** | D-06 |
| **日期** | 2026-05-06 10:15 |
| **决策者** | 用户 (minions) |
| **状态** | ✅ CONFIRMED |
| **结论** | 每个模块单独记录版本和状态，支持回退，防止版本回退混乱 |

### 原话引用
> "你需要清晰的记住这个架构，并且每做一部分要进行记录防止版本回退情况，
> 每一部分分别做记录和状态回退的设置；请你清楚的进行记忆分类，
> 确保后期不会忘记这个基础的要求和大的框架"

### 具体措施
1. `docs/MODULE-STATUS.md` — 全局模块状态追踪表
2. `docs/ARCHITECTURE.md` — 架构总纲（单一事实来源）
3. `docs/decisions/` — 决策记录
4. `docs/changelog/` — 变更日志
5. 每个模块有版本号、上一稳定版、回退点

### 影响范围
- 开发流程必须包含状态更新步骤
- 每次变更先改文档再改代码
